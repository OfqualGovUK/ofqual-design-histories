## Context

In the existing CMS, the case lists are inconsistent and hard to scan, resulting in reliance on external tooling and guidance to find cases. Each module had its own list layouts, metadata, status labels, business vocabulary and filters. This makes it harder for staff to work across different case types requiring memory of working with different cases instead of recognition of a consistent pattern. It also makes it more difficult for new staff to learn how to use the system.

The main problems are:
- different list layouts and vocabulary in each module
- unclear status information, making cases harder to find and scan
- inconsistent filters in modals that increase decision complexity and fail WCAG 2.2 criterion 2.4.11 Focus Not Obscured. 

## Options

We considered:
- keeping separate lists but improving labels and filters with closer alignment on business vocabulary
- creating a shared design pattern for lists but keeping module-specific lists and filters
- building a unified case list pattern with consistent layout, labels, vocabulary and filters

## Proposed solution

The first two options would still require staff to switch between lists to see any cases they are working on, and learn different data attributes for each case type. We chose to test the third option first because it simplifies navigation, encourages shared interactions and business vocabularies, and allows users to see a list of cases across case types. 

Paired with filtering and search to allow for views of all their cases, colleagues cases, team cases, all cases for a specific entity, or within date range for example. More information on filter designs will be included in a separate post.

### Case list design

The unified case list (Figure 1):
- uses a consistent data table pattern and shared metadata
- improves visibility of case statuses with clear labels and colour coding
- provides on-page filters that work the same way across cases.

![Screenshot of unified case list design showing the filters on page to the left hand side of the screen and the case list](picture1.png)
*Figure 1: Unified case list design*

The goal is to make case discovery faster, reduce reliance on external tooling and shadow IT, make the system more simple and flexible, and improve operational efficiency.

### Submitted by

As case types have different external user types (citizen, AO, PAO), we included a "Submitted by" column to combine the external user types in the list to help case workers identify cases more easily.

### Risks and mitigations

The risk is that a single list could become overwhelming if not designed well. We mitigated this by:
- using progressive disclosure to show fewer results at a time, with more details available on demand
- limiting the number of columns to the most important information (Case ID, Title, Case type, Submitted by, Recieved date, Status, Case lead)
- providing clear, consistent filters to help users narrow down results quickly

## Research

We tested the new design with case workers from 2 teams with experience covering multiple case types. In summary:
- overall the case list was understood and well received
- column headings were seen as sufficient for finding cases that the case workers typically work on.
- pagination was found and understood. Participants knew to either change the number of items per page or scroll through the pages to access further cases.​
- the participants were able to sort the table. However, they were confused by the unsorted state icon (Figure 2).
- all users were able to understand the status labels and their meanings quickly and easily.​
- users generally missed the search bar for the data table, but once they found it, they were able to use it successfully and understood it searched across all columns. 
- some users mentioned it would be helpful to search more broadly through case content for keywords or phrases.

![Screenshot of case list design showing the unsorted state icon](picture2.png)
*Figure 2: Unsorted state icon*

## Next steps

We plan to:
- test with more teams and case types, and with users of assistive technologies
- consider if we need to improve the visibility of search or observe if learnability is enough
- consider whether to add more advanced search options and feasibility in that space
- further think about risks around scalability and UX performance with quantity of cases
